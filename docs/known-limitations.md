# Known limitations and open decisions

The original plan is implemented except the items below, which are intentionally incomplete or blocked.

## Platform support

- **Compiler distribution:** prebuilt compilers (install script, `xlang self-update`, Homebrew tap) exist for
  macOS and Linux on arm64/amd64 only. There is no native Windows build of the compiler (it uses POSIX
  process and file APIs); Windows hosts use WSL. `self-update` and `scripts/install.sh` shell out to `curl`,
  `tar` and `sha256sum`/`shasum` instead of embedding an HTTP/TLS client and an archive reader; they verify
  the SHA-256 from the release's `checksums.txt`, which comes from the same GitHub release as the archive
  (integrity against corruption, not a signature). `self-update` never touches a Homebrew-managed binary.
  No release exists until the first `v*` tag is pushed. Options: embed a TLS client, sign releases.
- **Shell completion setup:** `xlang completions install` appends its block at the end of `~/.zshrc` and
  `~/.bash_profile`/`~/.bashrc`. If a user's own `compinit` runs after the end of `.zshrc` (rare), the zsh
  registration can be reset; move the block above it. bash completion needs no `bash-completion` package
  (it uses plain `complete -F`). Terminal emulators that start non-login bash on macOS read `~/.bashrc`, not
  `~/.bash_profile`; the block goes to whichever of the two already exists, else `~/.bash_profile`.
- **macOS threads (D1, option A):** pthread_create from libSystem is the creation primitive now (attribute stack is the top of the caller region, argument block at its bottom). The threads and scheduler e2e programs are being verified; see the e2e result before trusting this line.
  (MIG message), or keep the single-thread mode.
- **Windows:** `std/sys/windows.xl` imports ntdll `Nt*`, bcrypt (RNG) and `GetStdHandle`, and `std/sys/sock.xl`
  imports ws2_32 (sockets), each with `@library("...") declare fn`; the clock is read from `KUSER_SHARED_DATA`. A program cross-compiles and
  links (`--target x86_64-pc-windows-msvc`, import libraries generated by `llvm-dlltool`). **Tests:**
  `test/e2e/run.sh` builds every Windows-capable e2e program as a Windows executable and runs it with
  `cxrun <exe>` (CrossOver/Wine; skipped when `cxrun` is not on `PATH`): language, stdlib, file/JSON, all
  hash/AEAD/ECDSA/X25519 programs, and the TLS 1.3 server + client and HTTPS server + client pairs (RSA and
  ECDSA certificates, the 200000-byte transfer, host-name and root rejection) pass with the same results as
  macOS and Linux. **Not** run on real Windows (Wine's winsock/crypt32 are not Windows'), and the
  `sched`/`threads`/`panics` e2e programs are not run there. The entry stub (`mainCRTStartup`) exits through
  `NtTerminateProcess` and provides `__chkstk`/`_fltused` itself. Not done: threads (`NtCreateThreadEx` +
  `WaitOnAddress`), readiness polling (IOCP/AFD), pipes; the file API paths are widened as Latin-1 (only `fsListDir`, which
  needs a UTF-16 pattern, converts through `std/encoding/utf8`); the fd is the
  handle's low 32 bits (socket fds carry bit 30); `-D ssn...` no longer exists. Entry stubs exist for linux and macos on x86_64 and aarch64 and for windows on x86_64 only; the Windows stub is x86_64 assembly with no aarch64 variant. Every executable stub calls `_xl_initAll` (the `@init` functions) before the `@entry` function and `_xl_finiAll` (the `@fini` functions) after it.
- **Linux/macOS sockets ignore SIGPIPE** (`std/sys/sock.xl`: process-wide on Linux, `SO_NOSIGPIPE` on macOS), so a
  write to a vanished peer is an error return, never a crash. OS setup (WSAStartup on Windows, the Linux SIGPIPE
  disposition) runs inside `sockUp`, which every socket creator calls; user code never sees it. Not done: the
  public `std/net` layer on top of `std/sys/sock.xl` (IPv6, DNS, address types).

## ABI and interop

- **`export(c)` and aggregates by value:** structs are passed/returned through pointers (the xl convention),
  not through the target C ABI (SysV/AAPCS register passing). Only pointers, scalars and `@repr(c)`
  structs behind pointers are safe across the boundary.
- **Itanium typeinfo:** the vtable of an `@repr(c)` class has a `null` typeinfo slot; no `_ZTI...` symbol.

## Language/stdlib

- Control flow: `while`, `do { } while c`, `for init; cond; step { }` (each of the three parts optional),
  `for i in lo..hi { }` (`hi` exclusive) and `for i in lo..=hi { }` (`hi` inclusive), both with integer bounds
  evaluated once and an integer literal on one side taking the other side's type, `break`, `continue`, labels
  (`outer: while ...`, `break outer`, `continue outer`;
  `continue` in a `for` runs the step), `switch v { case a, b { } default { } }` (integers, bools, enums; no
  fallthrough; a `break` inside a `switch` leaves the enclosing loop, the `switch` is not a break target),
  `defer stmt` (runs when the enclosing block is left, including by `return`/`break`/`continue`, last-in
  first-out; the deferred statement cannot itself `return`, jump, declare a variable or `defer`; `return v`
  computes `v` before the deferred statements run), `cond ? a : b`, compound assignment (`+= -= *= /= %= &= |= ^=
<<= >>=`) and statement-level `x++` / `x--`. `a op= b` is `a = a op b`; a target containing a call is
  evaluated once through a hidden pointer. `++`/`--` are lexed as tokens, so `a--b` no longer parses as `a - -b`:
  write `a - -b`. Break/continue across a `switch` or `for` header are not otherwise restricted.
- Variadic packs (`..args`, core-language phase 12.1): a pack is a compile-time list, so each distinct argument count and
  type list is a separate instance and code size grows with the number of such calls. A pack cannot be indexed, cannot
  be used as a value, and a pack function cannot be `export(c)`, `declare`, virtual, generic or a method (`E0736`);
  there is no C-ABI form of a variadic function. Each argument of a `print`-family call needs a `fmtWrite` overload for
  its type, so an unsupported type fails at the call, not at the format string.
- Generics are instantiated per use (monomorphized). Not done: constraints on type parameters, generic methods outside
  a class (`E0733`), overloaded generic methods (`E0405`), and generic methods of an interface declaration (checked only
  when implemented or called). An overlap between two generic impl templates (`E0731`) is found only when an instance
  that matches both is used. Generic instances are not `linkonce_odr` (the whole program is one module). Expression-level
  `f<T>(x)` is recognized when the closing `>` is followed by `(`, `{`, `)`, `]`, `,`, `;` or the end of the line, so
  `i < j > (k)` is a generic call. `__builtin_needsDrop`
  and `__builtin_drop` take their type with `<...>`, not as an argument, because a type is not an expression. An error
  inside an instance is followed by one "in instantiation of" note per level, at most 8.
- **Boot and registrations (core-language phase 10).** The generated init entry is `_xl_initAll`, not `$xl$initAll`
  as the plan said: in the raw AT&T entry stub a `$` that starts an operand is an immediate prefix, so
  `call $xl$initAll` would not assemble. The Linux and macOS paths are verified only through the Docker e2e runs.
  **Allocator replacement is not tracked per block:** the stdlib `alloc`/`free` roles, `free`, `String` and `Vec` all go
  through `currentAllocator`, so after `currentAllocator = v` a block allocated before the assignment and freed afterwards
  goes to `v.free`. The compiler does not check the pairing, and a user `register(alloc)` without a matching
  `register(free)` frees through the stdlib `free`. `std/thread/sched` keeps using `Heap` and `sysMap` directly and is not
  redirected. **Compiler/runtime split (decision):** the compiler knows no allocator type and no method names; `new T`
  calls the registered `alloc` function, `delete p` the registered `free` function, and `new(p) T` is placement. The
  explicit-allocator forms `new(a) T` and `delete(a) p` and the builtin `__builtin_setRegistered` (and `E0728`) were
  removed. `String` and `Vec` still use the `Allocator` interface in `std/mem/mem` directly. A bodyless `@init fn boot();` is the parser's `E0002`; the sema check for a missing body in `E0729` is therefore only a
  guard.
- **Static libraries and objects own no entry:** `--emit=static` and `--emit=obj` export weak `_xl_initAll` and `_xl_finiAll` that run only the `@init` and `@fini` functions of that build. A linking executable keeps its own strong `_xl_initAll`, which runs the init functions of the program it was compiled as, so a prebuilt archive's init functions run only when the host calls that archive's `_xl_initAll` itself. Open decision: one init table per archive, or generated per-object init sections.
- **Shared libraries on Windows (open decision, needs confirmation):** `--emit=shared` builds a DLL with neither hook, so its `@init` functions do not run on load, its `@fini` functions do not run on unload, and its `@entry` never runs by itself; the host must call `_xl_initAll` and `_xl_finiAll`. A `DllMain` hook (DLL_PROCESS_ATTACH runs `_xl_initAll` and then `@entry`; DLL_PROCESS_DETACH runs `_xl_finiAll`) is not implemented, because Windows work is deferred by the project rules. Whether the Windows hook is in scope now is the open decision.
- **Entry arguments on Windows and in shared libraries:** the `@entry` argument form (`argc: i32`, `argv: **ui8`) is accepted only for executables on Linux and macOS (`E0755` otherwise). The Windows command line (`GetCommandLineW`) is not read yet. Open decisions: parse `lpCmdLine` in the stub or in `std/sys/windows.xl` and record the quoting rules; and whether a stdlib wrapper gives programs a typed view over the raw `argc`/`argv` form.
- **macOS unload hook does not run:** `_xl_finiAll` sits in `__DATA,__mod_term_func`, which dyld runs when an image is unloaded. A process exit does not unload a dylib, and `dlclose` is not called by the compiler or the stdlib, so `@fini` of a shared library does not run on macOS unless the host unloads it. This path is not verified at runtime.
- **Linux runtime of the entry stub and the shared hooks is checked only through Docker:** the Linux `_start` stub and the `.init_array`/`.fini_array` hooks are emitted and cross-built here, but they run only in the Docker e2e legs. The shared-library load test (`shared_hook`) runs on macOS only, through `DYLD_INSERT_LIBRARIES`.
- Tuples: `(A, B, ...)` is a product type, laid out in order like `@repr(c)`, and a function may return one. A tuple is taken apart with `local (a, b) = f()` or read element by element with `.0`, `.1`, .... A tuple is copied by value and needs no drop, so a tuple holding a value that needs drop (a class with a `drop` method) is not supported: the drop glue for a tuple is not generated. Nested destructuring (`local (a, (b, c)) = f()`) and destructuring in a `for` header are not implemented. A tuple element of a temporary tuple is not a place for `&` (see the address-of rule).
- Payload enums (sum types): the parser turns `enum E { A(T), B }` into ordinary items: the struct `E` (`tag`, `data`), the
  value enum `E$Tag`, the union struct `E$Data` and one struct `E$A` per variant with data. The union is not a language
  feature: only the compiler-made `E$Data` has `is_union` (all fields at offset 0), there is no `union` keyword. The
  names with `$` are visible in `xlang layout`; diagnostics name the enum, not its parts (a droppable array of a
  payload enum is `E0759`, and a droppable payload enum in a global or struct field is `E0758`). A droppable payload
  is allowed: the enum owns it and its drop glue drops only the live variant's value.
  A generic payload enum is one type made of those items: `Result<T, E>` makes `Result<i32, MyErr>` and, with it, the
  instances `Result<i32, MyErr>$Tag`, `$Data` and `$Ok`/`$Err`; a `case` always names the declaration (`Result.Ok`).
  `Result.Ok(v)` on a generic enum needs the target type where the value is created: the arguments are not inferred
  from the payload value or from a following `switch`, so `Result.Ok(1)` with no expected type (a typed local, an
  argument position, a `return`) is `E0756`.
  Not done: named payload fields, nested patterns (`case E.A(E.B(x))`), a payload
  pattern next to other variants in one `case`, `==` on payload enums and `switch` through a pointer without `*`.
  The tag is always `i32`.
- **Std sum types (`std/collections/option`, `std/collections/result`):** `Option<T>` and `Result<T, E>` are ordinary
generic payload enums plus a few helpers (`optionOrElse`, `optionIsSome`, `optionTake`, `resultOrElse`, `resultIsOk`,
`resultTake`, `resultTakeErr`). There is no `?` operator in the language, so early exit is written out as a `switch` on
both variants; the page in each file shows the shape. Known gap: `Option`/`Result` are re-exported through
`std/collections/index.xl` and `std/index.xl` with `export *`, and a generic type that reaches a program only through
such a chain of `export *` re-exports has been reported as not visible through `import "std"` while a direct import
(`from "std/collections/result" import Result`) and a namespace import (`import "std/collections" as C`,
`C.Result<i32, i32>`) work. No cause is confirmed yet.
- `Vec<T>` (`std/collections/vec`): the element accessors `get`, `first` and `last` return `*T` rather than a value, so a droppable element is never copied. `vecClone` panics for an element type that needs drop, because a bitwise copy would drop the element twice. The index panic text (`Vec: index I out of range for length L`) is built by `fmtIndexPanic` in `std/str/fmt`, on the stack and without allocating. `set` drops the old element through a plain `*slot = v` assignment. A drop-counter element type in `test/e2e/collections.xl` checks that `set`, `insert`, `remove`, `swapRemove` and `truncate` drop each element exactly once.
- `String` (core-language phase 7): the HTTP and TLS modules still use `*ui8` buffers. `fsReadAllString` is in `std/io/fs`.
- `const` (core-language phase 2): a `const` is not a `define` constant, so it cannot be an array length, a `staticAssert`
  operand or a `define` argument. Its initializer cannot read another variable or `const` (a `GlobalRef` is not a compile-time
  value), and an untyped module-level `const` takes only the default type of a literal (an enum member or an array needs
  `: T`). Block-level `const` names are not `define` names: they are read-only globals with a unique symbol.
- Ownership (core-language phase 5): drops are statically dispatched (deleting a derived object through a base pointer runs
  only the base drop). There is no explicit base constructor call: a derived `init` runs the base's argument-less `init`
  automatically. An array whose element needs drop is `E0721` at locals, parameters, fields and globals, because arrays do
  not drop their elements (`E0759` when the element type is a payload enum that needs drop; a droppable payload enum in a
  global or struct field is `E0758`). Temporaries used as receivers are materialized with a drop flag; a droppable
  temporary inside `&&`/`||` or a `?:` branch is dropped only if it was created.
- Overloading (core-language phase 3): an overloaded function's HIR name is its qualified name plus its mangled parameter
  types (not the link symbol); this is the unique key codegen uses. Overload resolution lowers each non-literal argument
  once, with no expected type, so an array literal passed to an overloaded or generic call has no element type context
  and must be written with a typed local. Nested overloaded calls cost time linear in their size. Class-to-base pointer
  conversion is not an implicit conversion in this language, so it does not count as a candidate. Virtual methods are not
  overloadable (`E0405`); `init` constructors are.
- **Slices (`[]T`, `[]mut T`, `buffer[..]`) and the iterating `for` (`for x in s`, `for x, i in s`): done,
  with open edges below.** A slice is a non-owning fat pointer `{ ptr: *T, len: usize }`, the same two
  words as `str` (`sizeOf([]T) == sizeOf(str)`, `ptr` at offset 0, `len` at offset 8). `[]mut T` has the
  same layout: `mut` is a permission, not a second representation. Semantics as implemented:
  (a) a slice never owns its bytes, so it needs no drop; a slice element type that needs drop is allowed
  in a read-only view but cannot be moved out (`E0720`, the `*p` rule);
  (b) a slice cannot be a field of an `@repr(c)` struct and cannot cross an `export(c)` boundary
  (`cCompatible` returns false, so it is a clear error, not a silent ABI change);
  (c) `buffer[..]`, `buffer[lo..hi]`, `buffer[..hi]` and `buffer[lo..]` build a slice; slicing a
  non-byte array or an existing slice yields `[]T` over its element type, and slicing a mutable
  owner (a local array, a `[]mut T`) yields `[]mut T`; `str` and `[ui8; N]` keep their old `str` result;
  (d) an empty slice is `len == 0` in practice; a slice value produced from `buf[1..1]` reads `ptr` as
  the base plus one element (not `nil`), because the lowering keeps the owner's data pointer; a truly
  nil slice can be written by hand and is legal to index `0` times;
  (e) indexing a slice is bounds-checked under `--safety=checked` (a panic, like an array); a `[]mut T`
  element is a place (`s[i] = v` writes the owner), a `[]T` element is read through the view;
  (f) `str` stays the read-only byte slice with a UTF-8 contract; the `[]ui8`-to-`str` bridge and the
  reverse are still `std/str` functions (`fromParts`, `view`), not compiler conversions.
  **The iterating `for`:** `for x in s { }` walks a `[T; N]`, a `[]T`, a `[]mut T` or a `str`; `for x, i
  in s { }` adds the index. Rules as implemented: the element is a pointer into the storage (`*T`, so
  nothing is copied and `x.field = v` writes the owner), and over `str` the element is `*ui8` (a byte;
  a rune form is a later decision); the index is a `usize` and comes *second* (Zig/Odin and `enumerate`
  order, not Go's `i, v` value-copy order); the bound is read once, so changing a length in the body
  does not move the end; `break`/`continue` and a label work as in the other loop forms. It is a pure
  compiler lowering to the hand-written index loop, no vtable and no `Iter` protocol.
  **Open edges:** a user-defined type is not iterable (an `Iter` protocol must choose between an
  `interface` call per element and a monomorphized generic, and there are no constraints, so it is
  deferred); `for x in vec` over a `Vec<T>` is **not** supported yet, because the compiler must not name
  a runtime type — `Vec` will be iterable once it can hand out a slice (`vec[..]`), which needs a stdlib
  `asSlice`; a `[]mut T` is a writable view with no alias or lifetime guarantee (there is no borrow
  checker), so `mut` marks intent, it does not forbid a second view of the same bytes;
  `for i, x in s` (index first) is rejected, the index is always second. Tests: `test/unit/slices.test.xl`,
  `test/unit/for_iter.test.xl` and `test/e2e/for_iter.xl`.
- `str` (phase 1 of the core-language work): no `==`/`!=` in the compiler (`eq` in std), no implicit or `as`
  conversion to `*ui8` (only `.ptr`), no way to make a `str` from a pointer except `std/str` (`strFromParts` reinterprets a
  `@repr(c)` two-word struct). A `str` view does not keep its bytes alive: the caller must. Writing through the `*ui8` of a
  literal is undefined behavior (its bytes are in read-only data); `[ui8; N]` is the writable form. `std/http` and the TLS
  modules still pass `*ui8` pointer and length pairs; their equality function is named `cstrEq` to avoid the name `eq` of `std/str`.
- `W0701`: a function with a return type can reach its end without `return`. The analysis is syntactic: every
  path must end in `return`, an infinite `while true` without `break`, `__builtin_asm(..., options("noreturn"))` or
  a call to the registered `panic`. Other `noreturn` callees are not recognized (a warning, not an error).
- Bit operators `& | ^ ~ << >>` exist with Go-style precedence (`& << >>` bind like `*`, `| ^` like `+`,
  so `a & b == c` is `(a & b) == c`). Shifts: the result has the left operand's type, the count may be any
  integer type, a count >= the bit width gives 0 (`>>` of a negative signed value gives -1), `>>` on signed
  types is arithmetic. In `define`/global constants `~x` is the untyped `-x - 1`; cast the result.
- `HIR` does not fold constant expressions (`N * 2` is constant in global initializers but folded later).
- Module resolution: `std`/`std/x` come from the stdlib root; other paths from the importing file's
  directory, then the root file's directory; a path under a dependency's repository path comes from that
  installed package (see [Packages]({{ site.baseurl }}/compiler/packages.html)). `import "x"` without alias binds the last path segment.
  There are no other search-path strategies.
- The default stdlib is embedded in the compiler (generated `build/gen/std_blob.cpp`, rebuilt when
  `std/**/*.xl` changes); `--std=<dir>`, `--std=host/user/repo[@tag]` and `[std]` in `xlang.toml` replace it.
  The compiler never searches the file system for it.

## Packages (`xlang package`, `xlang.toml`, `xlang.lock`)

Decisions taken when the package system was added ([Packages]({{ site.baseurl }}/compiler/packages.html) is the reference):

- **Git is the registry.** Packages are tags of git repositories, fetched by running the `git` executable
  (`ls-remote`, `clone --depth 1`); no HTTP client, no hosting API, no search, no publish command. Builds
  never fetch: `xlang package install` is the only command that uses the network. Go-style auto-download
  on build was rejected to keep builds offline and deterministic.
- **Integrity is the commit hash** recorded in `xlang.lock` (tag moved or cache edited = error). There are no
  content checksums or signatures; a compromised host or a force-pushed first download is not detected.
  A transparency log or checksum database is not planned.
- **No version solving.** One copy per repository per build; the project's own `[dependencies]` entry wins,
  otherwise two different required versions are `E0743`. No semver ranges, no "highest compatible" rule, no
  major-version import suffix (`/v2`): `v2.0.0` and `v1.9.0` of one repository cannot coexist.
- **Version rule:** release tags are `v?MAJOR.MINOR.PATCH`; a `-suffix` is a pre-release and a suffix
  ending in `test` a test tag; neither is ever `latest` (no fallback when only those exist: `E0744`), both
  install when named (`repo@v1.2.0-test`). A tag is not otherwise
  validated, so a `v1.0.0` that does not build is the publisher's problem.
- **Only exact tags, no branches or commits.** `version = "main"` or a commit hash is `E0742`; there is no way
  to track a branch except a `path` dependency on a checkout.
- **Dependencies of dependencies:** read from the package's `xlang.toml` (a package without one has none) and
  resolved transitively with exact tags only. A package's `[std]` is ignored; a stdlib package's own
  dependencies are not resolved. There is no `dev-dependencies` or optional-dependency notion.
- **`[[native]]` files are committed to the repository** and linked into executables and shared libraries
  only; `--emit=static|obj` do not include them. No download step, build step, or `url` form, and the compiler
  never runs a command from a package. Entries are chosen by `os` and `arch` only (no ABI/libc flavor, which
  is not a concept in xlang). A native file must be built `--no-std` if it is an xlang library (it would
  carry a second copy of the stdlib). Native inputs of dependencies that the program does not import are
  still linked.
- **No per-package compiler-version requirement** (`xlang = ">=0.x"` is not implemented), no `build.xl`
  hooks, no feature flags for packages, no `-D` forwarding to packages.
- **Package identity is the repository path.** A repository that moves hosts needs a `source` override or a
  rename of the import paths. Git `submodules` are not fetched. LFS files are not fetched.
- **Cache is per project** (`<root>/.xlang/cache`), not shared between projects, and old versions are never
  pruned automatically (`xlang package clean` deletes all).
- **POSIX hosts only** (fork/exec, `file://` URLs); the compiler has no native Windows build either.
- **`install` can leave downloaded sources in the cache** when a later package of the same run fails; the
  manifest and lock are untouched in that case.
- Package modules are keyed by their import path, which contains dots (`github.com/u/r`); mangled symbol
  names therefore contain dots too. `import "github.com/u/r"` without alias binds the last segment (`r`).

## Stdlib: files, JSON, HTTP

- **`std/http`:** the server speaks HTTP (`routerServe`) or HTTPS (`routerServeTls`, TLS 1.3; one connection
  at a time, blocking `accept`, `Connection: close`; a slow client stalls everyone for up to the 20 s receive
  timeout). The router is Gin-style (`:name`, `*name`, groups, middleware chains, 404/405, trailing-slash
  redirect). Limits: path 127 bytes, 7 middleware per route, 8 route parameters (512 bytes total), 1024 bytes
  of response headers; registration beyond them panics or fails. Request bodies need `Content-Length` (chunked
  request bodies are not supported); the request buffer is capped by `maxHeaderBytes`/`maxBodyBytes`. There is
  no panic recovery middleware, no body binding and no template/static-file helpers. Routes are matched by a
  linear scan (static first), not a radix tree.
  The client is `Client` (`Get`, `Head`, `Delete`, `Post`, `Put`, http and https, redirects); it has no
  cookies, keep-alive, compression, proxy, IPv6 or HTTP/2, and no streaming bodies. Source is split in `std/http/*.xl`.
- **`std/tls` is TLS 1.3 only, client and server:** X25519 key exchange, suites `TLS_CHACHA20_POLY1305_SHA256`
  (preferred) and `TLS_AES_128_GCM_SHA256`; no TLS 1.2 or older (a TLS 1.2-only peer fails with `TLS_ERR_VERSION`;
  the server answers it with a `protocol_version` alert), no session resumption/0-RTT/NewSessionTicket, no
  HelloRetryRequest (a client without an X25519 key share, or a server that insists on another group, fails with
  `TLS_ERR_RETRY`), no AES-256-GCM-SHA384, no client certificates (the client sends an empty Certificate when
  asked; the server never asks), no ALPN, SNI is sent but the server ignores it (one certificate per
  `TlsCredentials`, no virtual hosting). **Server keys:** PEM PKCS#8, PKCS#1 RSA or SEC1 EC (RSA up to 4096 bits
  signing rsa_pss_rsae_sha256; ECDSA P-256 / P-384; no Ed25519, no encrypted keys); a chain of at most 60000
  bytes; the leaf's key type must match the key. **Signing is not constant-time** (square-and-multiply and
  double-and-add on the secret; `k` for ECDSA is random, not RFC 6979): do not expose the server to a local
  attacker who can time it. Interop is verified against OpenSSL 3 `s_client` (both suites, RSA and ECDSA) in
  manual runs; the e2e suite uses the in-repo client. The test key pairs under `test/e2e/tls/` are public. Certificate
  validation (`std/tls/truststore`, `std/crypto/x509/x509`): chain to an OS root, validity period, `subjectAltName` DNS names
  (CN is ignored, IP SANs unsupported), CA/keyUsage/pathLen; **not** checked: revocation (CRL/OCSP),
  nameConstraints, extended key usage, critical extensions, certificate policies. Signatures: RSA PKCS#1/PSS and
  ECDSA P-256, P-384, P-521 and secp256k1; Ed25519 and Ed448. Root stores: Linux PEM bundles (`/etc/ssl/certs/ca-certificates.crt`
  and distro variants), macOS `/etc/ssl/cert.pem` (the keychain itself is not read), Windows: the system `ROOT`
  store through crypt32 (roots Windows would still fetch on demand from Windows Update are absent until used;
  enterprise/policy stores are not read; 4 MiB cap). The crypto is not constant-time (AES S-box, bignum),
  fine for a client verifying public data but not for secrets shared with a local attacker. Handshake messages
  are limited to 64 KiB and 8 certificates. The root bundle is cached unlocked (two threads racing the first
  load leak one mapping).
- **`std/encoding/json` is read-only and flat:** lookups of top-level members of an object in a NUL-terminated buffer;
  no nested paths, no `\u` escapes, no validation, no writer.
- **`std/io/fs` has no directories or metadata** beyond existence and size; the caller supplies all buffers.

## Testing

- **`std/testing/testing` has no discovery:** a test file registers its tests explicitly (`test(&s, "name", fn)`) and
  returns `suiteRun`. Auto-discovery of `fn test*` would need reflection or a compiler-side convention.
- **No chained matchers** (`expect(x).toEqual(y)`): the matchers are typed functions (`expectEq` for `i64`, `expectEqUInt`, `expectEqStr`, `expectNear`, ...).
- **`try` / `catch` unwinds panics only.** There are no typed errors (`Result`, `?`); that is a separate decision.
  The unwinder (`std/runtime/unwind`) walks frame pointers and uses a table of (function, landing pad) addresses, so:
  frames of foreign code (not compiled by xlang) cannot be unwound; the table covers the functions of the module being
  compiled, so separately compiled modules (`only_module`) are not unwound through; a function with `defer`, drops or
  `try` keeps every local in memory and is never inlined; a panic with no `try` runs no cleanup. Verified on macOS
  arm64 and Linux arm64/x86-64; `try` is an error on Windows (register snapshot not written). A cleanup that itself
  panics while unwinding is not handled. `xlang test` still ends the file's run on a `panic`; it does not use `try` yet.
  The compiler hooks this adds (`unwind` role, `__builtin_unwindPads`, `__builtin_unwindPadCount`, the `try` snapshot asm)
  are the only compiler knowledge of unwinding; the walker, registry and message copy are stdlib.
- **A failed expectation does not stop the test** (no unwinding); a `panic` ends the whole file's run, which
  `xlang test` reports as that file failing.
- **`xlang test` runs files sequentially** (no `--jobs`) and has no per-test name filter; granularity is the
  file. Windows is not supported by the runner (POSIX `fork`).

## Std cryptography (`std/crypto`)

- **AES is not constant-time:** the S-box lookups depend on the data. The modes and GCM inherit this. A caller that must resist cache timing needs a bitsliced AES, which is not implemented.
- **XTS needs whole blocks:** the data unit must be a multiple of 16 bytes. Ciphertext stealing (IEEE 1619 section 5.3.2) is not implemented; the call panics otherwise.
- **CBC does not pad:** the caller adds PKCS#7 padding or whatever framing it uses.
- **Not implemented, on purpose for now:** AES-CFB and AES-OFB (CTR covers the use cases), AES-OCB (RFC 7253), DES, RC4 (RFC 7465 forbids it in TLS), Blowfish, Twofish, Camellia, SM4, ARIA, SEED, CAST5, IDEA, RC2, RC5, RC6, Serpent, Kuznyechik, BLAKE3, RIPEMD, Whirlpool, Tiger, SM3, GOST, Streebog, Argon2, bcrypt, DSA, SM2, OCSP requests, PKCS#8 and PKCS#12 encryption, QUIC and DTLS. Each has a Turkish feature assessment in the plan (std.plan.md, "Deferred").
- **concat_kdf and X9.63 have no test vector yet:** `concatKdf` and `x963Kdf` follow the one-step construction of NIST SP 800-56C and ANSI X9.63; their outputs are not compared with a published vector.
- **HKDF over BLAKE2 is not defined:** BLAKE2 has no HMAC block size here (see `std/crypto/hash/digest`), so `hkdfExtractAlg` and `hkdfExpandAlg` reject the BLAKE2 ids.
- **RSA key generation is not constant-time and uses a fixed exponent:** `rsaGenerateKey` always uses e = 65537 and runs data-dependent arithmetic on the primes.
- **Streaming HMAC is not implemented:** `hmac` takes the whole message in one buffer; a long message needs the caller to buffer it.
- **BLAKE2 keyed mode is checked only for the unkeyed vector:** the keyed path shares the code but has no separate published vector in the tests yet.

## Std mathematics (`std/math`)

- **Floating-point accuracy is checked to 1e-9, not to full double precision:** the elementary functions were compared with `bc -l` on about twenty sample points. The trigonometric reduction uses a two-part pi/2, so accuracy falls off for arguments much larger than 1e6.
- **Floating-point functions are not correctly rounded:** results can differ from a libm in the last bit.
- **`pow` with a non-integer exponent** goes through exp and log and loses about |y log x| times the rounding error.
- **Big-integer arithmetic is not constant-time:** the division and Montgomery code branch on data.
- **`BigInt` has a fixed bound of 130 limbs (4160 bits):** it is the operand size of the `bignum`/`bigdiv` limb
  functions, so an operation whose result needs a 131st limb panics (`BigInt: result exceeds 4160 bits`) instead of
  growing; `modPow` also needs an odd modulus (Montgomery reduction). The type has no operator overloads: an
  operation is a method with a destination (`out.add(&a, &b)`), and `sub` panics when the right operand is larger
  because the value is unsigned.
- **The geometry value classes are heap-free but not chainable:** `Vec2`, `Vec3`, `Vec4`, `Rect`, `Mat2`, `Mat3`, `Mat4`,
  `Quat` and `Transform` are classes with `f64` fields, an `init` and methods, so only `Mat` allocates (from the
  registered allocator). The language has no associated (static) function and no address of a temporary, so a named
  zero/identity factory is not available as a method (`Vec3(0.0, 0.0, 0.0)`, and the free functions `mat2Identity`,
  `mat3Identity`, `mat4Identity`, `quatIdentity`, `transformIdentity`), and the result of a method must be stored in a
  variable before another method is called on it (`a.add(&b).normalized()` is `E0709`). Every product also has an
  out-parameter form (`mulTo`) for that reason.
- **A field assignment whose right side reads another field of the same object computes a wrong value:** the current
  code generator miscompiles `self.p = Vec3(self.p.x + dx, ..)` and `a.x = a.y` style statements, so every such place in
  `std/math` copies the fields into locals first. This is a codegen defect, not a language rule.

## Std random and identifiers (`std/random`)

- **cuid v1 fingerprint is random per process:** the reference uses a hash of the host name. No host name is read (it needs an OS call that is not in std/sys yet). Values from two processes differ in those 4 characters even on the same host.
- **cuid v2 hash is SHA-256:** the reference uses SHA-3. Values differ from the reference until SHA-3 exists in `std/crypto` (plan Q2). The text is the lowest 23 base36 digits of the hash, not a substring of its text form.
- **XID machine and pid bytes are random per process:** the reference hashes the host name and uses the real pid. Same consequence as cuid v1.
- **Time is the caller's:** every generator takes the time as a parameter because `std/sys` gives seconds only. Millisecond and monotonic clocks are todo (plan section 8b and section 22).
- **Snowflake-family layouts are not standards:** Snowflake, Sonyflake, Instagram and TSID describe the layout of their own projects; the epochs are the projects' published values, and Instagram's epoch is the caller's.
- **Sqids and Hashids are not implemented:** neither has a specification, so the output would be defined by this library alone.

## Std text API (`std/str`)

- **`view` returns a `str` on purpose:** it is the zero-copy byte primitive used inside the stdlib and by byte-level code (`fromParts`, `fromC`, `view`, and the `str` parameters of `eq`, `find`, `compare`, `globMatch`). Every function that returns text as a value returns `String`. Keeping `view` public is a decision: remove it when the compiler converts `str` to `String` views on its own.
- **`String` methods returning views:** `asStr` returns a `str` view of the String's buffer, valid until the String changes or is dropped. This is the only view-returning method; the copying methods return `String`.
- **Glob syntax has no escape:** `globMatch` treats `*` and `?` as wildcards in every position, so a literal `*` or `?` cannot be matched. A bracket class and an escape byte are not implemented.

## Event polling and OS library calls

- **Readiness polling per OS:** Linux uses epoll (`epoll_create1` 291, `epoll_ctl` 233, `epoll_wait` 232 on x86-64; `epoll_pwait` 22 with a null sigmask on arm64). macOS uses kqueue (`kqueue` 362, `kevent` 363, struct kevent 32 bytes). Windows uses WSAPoll, the only readiness call Winsock offers. All three keep one-shot interests, matching EPOLLONESHOT and EV_ONESHOT.
- **WSAPoll limits:** it reports sockets only, not file handles; the process holds at most 256 watches across all poll sets; an empty set returns at once instead of sleeping for the timeout, because WSAPoll rejects an empty array. The poll-set owner is a process-wide counter, not a handle.
- **IOCP is not used:** it is a completion model (the kernel performs the I/O), so it cannot sit behind the readiness API. A proactor layer is a later decision.
- **Windows poll is not run on real Windows:** the code is type-checked for `x86_64-pc-windows-msvc` only, so its behavior is unverified.
- **Reachability pruning limits** (`src/hir/prune.cpp`): reachability is per call graph, so a path the program can take keeps its `@library` imports (for example `print` reaches the Windows socket write branch through `sysWrite`); the roots include every vtable and interface method, which keeps classes and impls whole; Linux `-l<name>` needs a static archive on the linker's search path, and the compiler adds no search path; dynamic linking on Linux (PT_INTERP, PLT/GOT) is not implemented.

## Tooling

- Debug info has compile unit, subprograms, line locations and basic types; no struct/class types.
- `--incremental` caches per-module objects only; semantic analysis still runs for every module (no
  interface files). A MIR layer (plan 8.3) was not needed.

## Std data formats (`std/encoding`, `std/compress`)

- **Compression is fixed-Huffman only:** `deflateFixed`, `gzipCompress` and `zlibCompress` write one fixed-Huffman block with greedy matches; dynamic-Huffman blocks, lazy matching and the zlib compression levels are not implemented. zstd, brotli, LZ4 and Snappy are not implemented.
- **CSV records are read one at a time:** a quoted field that spans lines needs the caller to join the lines.
- **JSON is not a tree:** `jsonPointerGet` and `jsonSkipRaw` return raw views; building a tree or a typed object model is not implemented.
- **Output buffers are fixed:** the decoders and the writers take the capacity from the caller and report overflow; there is no growing decoder yet.

## Std authentication (`std/auth`)

- **JWS algorithms:** HS256, RS256, ES256 and EdDSA are verified; ES384, RS384, RS512 and PS256 are not. JWK sets and key selection by `kid` are not implemented.
- **No claim validation:** `exp`, `nbf`, `iss` and `aud` are not checked; a caller reads them with `jsonPointerGet` and decides.

## Std time, versions and encodings (`std/time`, `std/semver`, `std/encoding`)

- **No time zones:** `std/time` is UTC only. The TZif format (RFC 8536) and the zone rules are not read.
- **No ISO 8601 variants:** only the RFC 3339 form is parsed and written; week dates, ordinal dates and durations are not implemented.
- **No version ranges:** `std/semver` compares versions only. Caret, tilde and range syntax are not implemented.
- **CBOR reader only checks and skips:** `cborReadHead` and `cborSkip` do not build values (no map or array objects, no float conversion). Tags are skipped, not interpreted.
- **Protobuf is primitives only:** varints, zigzag, tags and fixed-width values. No message schema, no generated code and no group wire type.
- **Base58 has input caps:** `base58Encode` takes at most 512 bytes of input and `base58Decode` produces at most 800 bytes.

## Std OAuth helpers

- **No token exchange:** `std/auth/oauth` builds the authorization URL and the PKCE values; the token request and response handling (RFC 6749 section 4.1.3) are not implemented here.

## Time zones

- **POSIX DST rules are not evaluated:** after the last transition of a zone with DST, the last transition type is used. Dates beyond the table (the files list transitions to 2037 for most DST zones) would need the footer rule evaluated (RFC 8536 section 3.3).
- **Zone files are read by the caller:** the module parses bytes; it does not look up `/usr/share/zoneinfo` or the Windows zone registry.

## TOML

- **TOML validation does not catch duplicate keys or table redefinitions:** the module checks the grammar without a tree. A caller that loads configuration must detect repeated keys itself.
- **TOML lookup is by written key:** `tomlGet` compares keys with the quotes and blanks removed; escapes inside quoted keys are not processed, and a repeated `[[array]]` header returns its first occurrence.

## Std network protocol messages (`std/net/proto`), CSR and CRL, MessagePack

- **NTP is one query:** `ntpQuery` does one request and reply; the clock filter, peer selection and the clock discipline are not implemented.
- **SOCKS5 without authentication:** only the "no authentication" method (RFC 1928). The username and password subnegotiation (RFC 1929) is not done.
- **Syslog has no transport:** the RFC 5424 header is written; sending it, the structured data and parsing received messages are not implemented.
- **Certificate requests and CRLs are read only:** `csrParse` and `crlParse` do not read attributes or extensions, and no request or CRL is written or signed. Key writing covers SubjectPublicKeyInfo (RSA, EC) and EC PKCS #8 only; RSA private keys need the CRT values, which `PrivKey` does not keep.
- **Punycode without nameprep:** `idnaLabelToAscii` does not case-fold or normalize (RFC 3491). Callers must pass prepared labels.
- **MessagePack reader skips only:** `msgpackSkip` checks structure; `msgpackReadUint` reads unsigned integers. No general value decoder.
- **DNS wire format builds queries only:** `dnsBuildQuery` writes one question with RD set; responses are read with `dnsReadName` and `dnsParseHeader`. Answer records (A, AAAA, MX, TXT) and EDNS are not parsed; the blocking resolver in `std/net/dns` is separate.
- **No raw sockets:** the IPv4, IPv6, ICMP, UDP, TCP and ARP builders write bytes and checksums only; sending them requires raw sockets, which are not wrapped.
- **TCP has no state machine:** `tcpBuild4` writes a 20-byte header with no options (no MSS, window scale, timestamps or SACK). Connection setup, retransmission and congestion control are not implemented here.

## Std elliptic curves (`std/crypto/sig`)

- **Ed448 and the other Edwards curves use the slow path:** the scalar reductions go through the integer routines (`bigintDivMod`), not Montgomery form, so an Ed448 signature takes far longer than an Ed25519 one.
- **Ed448ph (the pre-hashed variant) and contexts are not implemented:** only the pure Ed448 signature with an empty context (RFC 8032 section 5.2.6, phflag 0).
- **secp256k1 uses the same non-constant-time arithmetic as P-256:** a public key, a signature and a shared secret match openssl, but a secret scalar is processed with data-dependent branches.

## Std HTTP router (`std/http/router`)

- **No RedirectFixedPath and no internal redirect:** the router redirects a missing or extra trailing slash (`redirectSlash`), but it does not fix a case-insensitive path, and `HandleContext`-style forwarding of a request to another route is not implemented. A handler that needs another route calls the handler directly.
- **Fixed sizes:** a route pattern is at most 128 bytes, a group prefix at most 128 bytes, and a chain at most 8 handlers (middleware included). A longer pattern stops the program.
- **Form and body binding:** `c.body` is the raw body; there is no `PostForm`, multipart or `ShouldBindJSON` equivalent yet.

## Std system information (`std/cpu`, `std/hw`, `std/gpu`, `std/io/dir`)

- **Windows is partly empty:** `hwProductName` and `gpuDrmDevices` return 0 there. Windows has no registry-free local
  query for the machine model (DMI/SMBIOS is not exposed by kernel32; the registry keys
  `HARDWARE\DESCRIPTION\System\BIOS` and `HARDWARE\DESCRIPTION\System\CentralProcessor\0` need `RegGetValueW`), so the
  product name is left empty rather than guessed; GPU enumeration needs DXGI, which is not wrapped. The CPU description is
  `hwCpuModel` from the `PROCESSOR_IDENTIFIER` environment variable, which names the family and model but not the marketing
  name (`ProcessorNameString` in the registry is the only source for that).
- **Windows arm64 CPU flags have no SHA-3/SHA-512/CRC32 source:** `IsProcessorFeaturePresent` reports the Armv8 crypto
  extension as one flag, so `sha3`, `sha512` and `crc32` are false on arm64 Windows.
- **Windows directory listing and guarded mapping are unchallenged at runtime:** `fsListDir` (`FindFirstFileW`) and
  `sysMapGuarded` (`VirtualAlloc` + `VirtualProtect`) are type-checked for `x86_64-pc-windows-msvc` and `aarch64-pc-windows-msvc`
  only; no e2e entry exercises them, and a symlinked directory reports kind 4 (the reparse point is not resolved).
- **macOS has no directory listing and no GPU enumeration yet:** `getdirentries` is not in the verified XNU table; Metal and IOKit are deferred.
- **The DRM success path is untested:** no DRM driver exists in the available containers, so `DRM_IOCTL_VERSION` is only exercised on a missing or non-DRM node.

## Std HTTP conformance (`std/http`)

- **Open HTTP rules:** keep-alive (every response says `Connection: close`), several differing `Content-Length` values (the first is used), and target-form validation (absolute URI and `*` forms are routed as paths). See docs/std/http-audit.md.

## Std MQTT (`std/net/proto/mqtt`)

- **Packets only:** the builders write CONNECT, PUBLISH, SUBSCRIBE, PINGREQ and DISCONNECT, and the reader parses CONNACK. The connection loop, the QoS 1 and 2 acknowledgements, will messages, credentials and AUTH are not implemented.

## Batch: process, stat, io_uring, protocols, DER and hardware (this change)

- **io_uring is a standalone backend:** `std/sys/uring` sets up a ring and does a NOP round trip. The event loop (`std/sys/event`) still uses epoll; wiring the completion backend in with the epoll fallback is open. Docker's default seccomp profile refuses io_uring, so the fallback path is what runs in containers.
- **Process spawn has no environment:** `processSpawn` starts the child with an empty environment; passing one is open. There are no signal handlers (rt_sigaction, sigaction). `processSpawnOut` (child output into a file) is implemented for Linux and macOS only and returns -1 on Windows, so the xlang e2e runner (`test/e2e/runner.xl`) does not run there yet; its Linux path is not verified on a Linux host. The runner also lacks the shared-library load test (needs `DYLD_INSERT_LIBRARIES`, but a child gets an empty environment) and a per-test timeout.
- **Fiber scheduler is not built:** `sysMapGuarded` gives the guard page; the fiber scheduler on top of it is open.
- **Address-configuration clients are pure state machines:** `DhcpClient`, `Dhcp6Client` and `SlaacClient` do no I/O and read no clock (see docs/std/protocols.md). No ARP probe after a DHCPv4 ACK (`decline` is there for the caller), DHCPv6 handles one IA_NA (no IA_TA, prefix delegation, rapid commit or reconfigure), SLAAC uses the first prefix of an RA, one RDNSS address, no privacy addresses (RFC 8981) and no stable-privacy identifiers (RFC 7217).
